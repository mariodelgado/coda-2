Front matterWho this is for

Coda 2 is a three-pane instrument for a quantum processing unit: parameter-drift landscape on the left, the 3D device in the center, the cryostat plate on the right, and a chat dock across the bottom. It is a control plane, and it is a stage. Three roles use one instrument. They do not do the same job.

Beyond a chat window

A normal chat window is a transcript. You type, a model replies, and any physics lives only in sentences that scroll away. Coda 2 is instrument-first. The first thing you learn is the stage in FIG. 0: drift on the left, the device in the center, the cryostat on the right. Language is one channel, not the only surface. Physics stays in view while you talk. The chips in the dock are one-click goals.

  • Visual — the three panes: left drift landscape, center 3D device with the readout card, right cryostat plate.
  • Text — natural-language goals and the agent transcript in the dock.
  • Math — fidelity, Δf, T1 / T2, ToolTraces, and the metrics.

A chat-only UI can accept the same sentence and still hide the machine. Here the stage does not yield to the transcript. You drag the splitters, read the numbers, and send a goal without leaving the instrument. Use FIG. 0 as the picture of the product. The stills later in this book are the same three-pane chrome, not the older one-pane or two-pane layouts.

Quantum control engineer

You build and maintain the control software. A goal enters as POST /goals. The agent maps the goal to a tool. Every tool call writes a ToolTrace.

You keep the QPUAdapter seam. The waist is six methods: submit_job, poll_job, cancel_job, get_device_state, get_calibration, apply_calibration_update. The calibration loop measures fidelity, decides, applies an update, and measures again. The three metrics are time-to-calibrated, calibration success rate, and interface latency.

The default path is offline. It does not need a language-model key. If an optional planner is on, it falls back to the same rules. You extend the tools, or you replace the adapter. You keep the seam.

QPU operator

You run the instrument. You calibrate, check readiness, run circuits, and cancel jobs. You land on the idle home. The toolbar shows LIVE when the UI is connected. It shows READY centered when the device is fit for a circuit. You send a goal with a chip, or you type in the composer. Recalibrate when the state chip falls back to DRIFT, or when Δf grows. High Δf means the controls are off-target.

Read fidelity as Q0 percent in the toolbar and on the readout card in the center pane. Read the left pane for drift (orange applied versus blue true). Read the right pane for the cryostat plate and the status strip under it. The state chip sits at the far right.

Technical lead

You evaluate Coda 2 for your stack. You are a technical lead or a buyer of the integration. You use the same product the operator uses. You do not run a separate trial.

You follow one path: calibrate qubit 0, see READY, then run a Bell pair. You read the three metrics. You read the adapter seam. A simulator stands in for the device until a hardware adapter is connected. Your driver replaces that simulator behind the same six methods.

Not for This manual is not a cryogenics handbook. The millikelvin figure is computed from fidelity on the simulator. It is not a fridge sensor. The right-hand plate is an isometric drawing, not a fridge readout. Coda 2 is not an open chat for science or finance. The planner accepts four goal families. If a sentence matches no keyword, the planner checks device state, then it runs a soft calibrate. That is the catalog.

You see and manipulate properties of a quantum computer in the format that fits the moment. Dock layout (conversation shape)

The stage is three panes with two splitters between them. The dock sits at the bottom, over a bottom-third frost. Read the bottom of every screenshot top-to-bottom:

  1. Chat transcript — scrollable turns. Each turn has a you line (the goal) and an agent line (plain-English narration from agent_message). Tiny tool pills may sit under the reply; they are secondary.
  2. Chips — Calibrate Q0 · Bell pair · Q0 readiness · Device status · Improve Bell · Diagnose Q0 (one-click goals).
  3. Composer — type a goal and send (or ⌘K). Lowest control in the dock.

The three-pane stage extends under this dock. Panes start roughly equal. Left: high-contrast drift grid, coplanar with the fidelity surface. Center: the 3D device — qubit spheres Q0 and Q1, chiplets, resonators — plus a readout card at top right (Q0 / Q1 fidelity, T1, T2, err, mK). Part 1Mental model

Start with the machine. Then look at the plug. A QPU is a set of two-level systems. Classical pulses steer them. Readout returns classical bits. The device drifts. This software sits above that stack. Natural-language goals and an orchestrator call a narrow QPUAdapter. The backend stands in for cryo and electronics. Four nouns remain clear once that seam is visible: goals, tools, jobs, and the calibration loop.

1.1 How a QPU works

A quantum processing unit is not a CPU with exotic opcodes. It is a small set of engineered two-level systems (qubits). Microwave and baseband electronics couple to those qubits. A cryogenic environment keeps thermal noise low so coherence lasts. Classical software decides which pulses to send. The physics decides what you get back. The primer below is the minimum model an operator or agent author needs.

1.1.1 Qubit modality — superconducting transmon

This manual uses a superconducting transmon as the example modality. A transmon is a Josephson junction with a large shunt capacitor. That circuit forms a weakly anharmonic oscillator. The two lowest levels are the computational states |0⟩ and |1⟩. A readout resonator couples to the qubit. A microwave drive (XY) rotates the state. A flux or Z bias sets the qubit frequency when the junction is tunable. Other modalities (spin, trapped ion) differ in device physics. They still use pulses for control and a classical result for readout.

FIG. 1.1Qubit modality — superconducting transmon with readout resonator, XY drive, and flux/Z bias.

The chip holds a transmon and a readout resonator. The Josephson junction sets the nonlinearity. The shunt capacitor sets the charging energy. XY microwave pulses rotate the state. Flux bias sets frequency on tunable devices. Readout probes the resonator and returns a classical bit. This figure shows real QPU physics. This product uses a noisy simulator — see FIG. 1.5.

Cite. P. Krantz et al., “A quantum engineer’s guide to superconducting qubits,” Appl. Phys. Rev. 6, 021318 (2019); arXiv:1904.06560 — https://arxiv.org/abs/1904.06560

1.1.2 Cryogenic and RF stack

Room-temperature racks hold the AWG, DAC, local oscillator, mixers, digitizer, and control PC. Drive lines go down through the dilution refrigerator. Stages typically run at about 300 K, 4 K, still (~1 K), and the mixing chamber (MXC, ~10–20 mK). Attenuators on the drive path cut thermal noise into the qubit. The readout path amplifies a weak response: a TWPA near the sample, then a HEMT at 4 K, then room-temperature electronics. The sample package sits at the MXC.

FIG. 1.2Cryogenic / RF stack — 300 K rack through MXC, with attenuation down and amplification up.

Drive signals move down the fridge. Attenuators protect the qubit from room-temperature noise. Readout signals move up. A TWPA and a HEMT amplify the weak probe response. The digitizer turns that response into bits. This stack is real QPU infrastructure. The product stands in for it with NoisySimulatorBackend (FIG. 1.5).

Cite. P. Krantz et al., Appl. Phys. Rev. 6, 021318 (2019), arXiv:1904.06560; Keysight, “Characterizing Superconducting Qubits” application note — https://www.keysight.com/us/en/assets/3120-1387/application-notes/Characterizing-Superconducting-Qubits.pdf

1.1.3 Control and readout loop

Gates are the logical recipe (X, Y, CZ, Rz, and others). Pulses are the physical voltages and microwave envelopes. An AWG and LO emit those envelopes. Fridge wiring carries them to the qubit. The qubit state evolves. A readout chain amplifies the resonator response. A digitizer yields a classical bitstring. The classical PC classifies the bits, logs them, and decides the next pulse sequence. Fidelity is the rate at which those bits match the intended result.

FIG. 1.3Control and readout loop — pulse sequence → AWG → fridge → qubit → readout chain → digitizer → PC.

Control is continuous and analog on the wire. Readout is discrete and classical in the log. An agent does not speak in volts. It speaks in goals. Every successful goal becomes a pulse schedule and a measured bitstring. Wrong amplitude, frequency, or timing rotates the wrong amount. Fidelity falls.

Cite. P. Krantz et al., arXiv:1904.06560; IBM Qiskit Pulse (backend control / Schedule) — https://docs.quantum.ibm.com/api/qiskit/0.46/pulse; Keysight, “Characterizing Superconducting Qubits” — https://www.keysight.com/us/en/assets/3120-1387/application-notes/Characterizing-Superconducting-Qubits.pdf

1.1.4 Calibration as a closed loop on that stack

The device moves. Temperature, LO phase, flux bias, and cable response wander. Applied parameters drift away from the true sweet spot. That gap is detuning. As detuning grows, gate fidelity falls. Circuits stop being useful. Calibration is a recurring loop: measure, decide whether to move knobs, apply an update, and remeasure. Knobs include amplitude, frequency, and timing. Observables include gate fidelity, readout fidelity, and (on hardware) T1/T2-class metrics. This simulator reports a fidelity kernel instead of full T1/T2.

FIG. 1.4Calibration as a closed loop — knobs (amplitude, frequency, timing) and observables (fidelity, readout fidelity; T1/T2 on hardware).

Drift moves true parameters. Detuning is the measurable gap. Fidelity decay is why you care. Stop when best fidelity meets the threshold (default 0.88) or iterations end. Without remeasurement against a threshold, calibration is not an agent tool. It is a hope.

Cite. N. Wittler, F. Roy, K. Pack, M. Werninghaus, et al., “Integrated Tool Set for Control, Calibration, and Characterization of Quantum Devices Applied to Superconducting Qubits,” Phys. Rev. Applied 15, 034080 (2021) — https://journals.aps.org/prapplied/abstract/10.1103/PhysRevApplied.15.034080

1.3 Goals

A goal is a short natural-language string. An operator or agent submits it. Examples the deterministic planner accepts: “Bring qubit 0 to ready”, “Run a Bell pair and report fidelity”, “Report device health and temperature status”, “Check qubit 0 health and readout status”, “cancel <job-id>”. Goals enter through POST /goals or the UI composer, chips, or ⌘K palette. They are not LLM prompts by default. The planner in orchestrator/planner.py maps them to a list of ToolCall records. Optional LLM planning exists behind CONDUCTOR_ENABLE_LLM. It is off by default. The product path is offline-first.

1.4 Tools

The orchestrator registers five tools: calibrate_qubit, run_bell_pair, get_device_state, get_job_status, cancel_job. Each call produces a ToolResult and a ToolTrace (tool name, args, latency, ok, summary). Traces are the observability product. They show real control-plane decisions. They are not narrative fiction. Heavy paths (calibrate_qubit, run_bell_pair) cross the adapter. The other tools give visibility and guardrails.

1.5 Jobs

A QPUJob is a typed record. It has a JobType (calibration | circuit | diagnostic) and a JobStatus (queued → running → succeeded | failed | cancelled). The adapter owns submission and polling. 1.6 The calibration loop

Calibration is measure → decide → apply → remeasure. Continue until best_fid ≥ threshold or iterations end. That loop makes an agent interface viable. Each step has a typed result, a latency sample, and a fidelity point the UI can plot. Without the loop, “calibrate” is a fire-and-forget RPC with no story. Part 2Theory of the interface

This part states why an NL-goal and tool-using agent layer on a narrow QPU adapter is the right seam for calibration-heavy quantum ops. It also states where this system’s honesty line cuts. It is the intellectual core of the book.

2.1 The problem the interface solves

Quantum hardware drifts. Before a circuit is worth running, someone — human or agent — must decide whether to calibrate, which knobs to move, whether the move helped, and how that correlates with downstream job quality. Vendor pulse APIs expose the knobs. They do not expose the decision loop as a first-class, observable object. Chat-only LLM UIs expose language. They do not expose continuous detuning, fidelity climb, or a tool ledger operators can audit.

The AI→QPU integration layer asserts a third surface: goals in, typed tool traces out, device physics behind an adapter. Calibration is not a side effect of “run circuit”. It is an explicit tool with a success predicate and three metrics.

Rule of thumb If an operator cannot point at a ToolTrace row and a fidelity history for a calibration attempt, the control plane is not yet agent-ready. It is still a pulse console with a chatbot taped on.

2.2 NL goals and tool-using agents vs bare pulse APIs

Bare pulse APIs are necessary and not enough. They are the contract a driver must honour (load waveforms, arm triggers, commit cal tables). They are the wrong API for an agent that reasons in tasks: “bring Q0 to ready”, “don’t run Bell until ready”, “cancel the stuck diagnostic”. Agents need a small catalog of tools with stable names and JSON-shaped results. Humans need the same catalog as chips and a composer, not as a 200-method SDK.

This system’s planner is deliberately simple and deterministic. That is a feature for a founder demo: the mapping from goal text to tools is auditable in one function. When CONDUCTOR_ENABLE_LLM=1, an optional OpenAI planner may emit the same ToolCall schema. The execution path, traces, and metrics do not change. The interface’s value is the tool surface and the loop, not the quality of the NL parser.

FIG. 2.1Three concerns, one direction. Intent (agent) decides. Contract (adapter) admits only typed operations. Physics/noise (backend) is replaceable.

2.3 Intent vs device contract vs physics

Separating the three layers is the design claim.

  1. Intent lives in the orchestrator and planner. It answers: what should we do next, given a goal? It records ToolTraces. It must not embed vendor pulse details.
  2. Device contract is QPUAdapter: six methods. Anything that can sit under those methods — noisy sim today, AWG driver tomorrow — is a valid backend. The factory (adapter/factory.py) is the only place that chooses.
  3. Physics / noise lives in the backend. Drift rates, fidelity kernels, Bell contrast, firmware temperatures — none of these belong in the planner. On the stub, physics is explicitly “not connected”.

This separation lets a founder say: “keep the UI and the orchestrator; swap the adapter.” Without it, every UI widget hard-codes simulator assumptions. The project then fails at the first real fridge.

FIG. 2.2The six-method waist. submit/poll/cancel for jobs; get_device_state for health; get/apply calibration for the loop.

2.4 Closed-loop calibration as the viability reason

Open-loop “set these params” is not enough for agents. Agents need a stop condition and a progress signal. The CalibrationService supplies both: a threshold (default 0.88) and a per-iteration fidelity history. The algorithm is gradient-free on purpose — coordinate jitter with an annealing-flavoured acceptor — because this system’s job is to exercise the control-plane loop, not to win a tuner bake-off. Strategy objects can replace the sampler later. The metrics and traces stay.

Each apply samples interface_latency. Successes accumulate time_to_calibrated. Attempts accumulate the success rate. Those three numbers are the dials a skeptical quantum+ML founder should watch in the demo. If they move for the wrong reasons (or never move), the loop is fake.

FIG. 2.3Viability diagram: without remeasurement against an explicit threshold, calibration is not an agent tool — it is a hope.

2.5 Observability and trust surfaces

Trust in a control plane is not a green checkmark. It is a set of surfaces an operator can reconcile:

  • Fidelity history — climb chart with threshold reference line (UI HUD + in-rail details).
  • mK / coherence / readout — device state snapshot from get_device_state.
  • Param drift / detuning — get_detuning exposes |applied − true| on the sim (the problem calibration solves). The WebGPU surface places cyan (true) and amber (applied) markers on a Δfreq × Δamp landscape.
  • Tool ledger — ToolTrace rows: which tool, which args, latency, summary. The dock ledger is this list rendered as turns.

If any one of these is missing, agents can lie politely. With all four, a failure (fid cap, max iters, stub backend) is legible.

Chat is a fine composer. It is a poor primary surface for a drifting physical system. Quantum ops need continuous state in the visual field: readiness, temperatures, detuning, the spatial relationship of applied vs true. A chat transcript buries those in prose and scrolls them away. The system’s UI makes the stage the hero (~65% of the vertical field, full-bleed under the dock) with tabs for the WebGPU drift landscape and the 3D device panel. 2.7 Limits: sim vs hardware, toy timings, what changes on a real QPU

Honesty This is a control-plane demo, not a physics engine. Fidelity is a smooth function of parameter error with a wide basin so a simple search can climb. Drift is accelerated for demo feel. Interface latency on an in-process simulator is not predictive of RPC/firmware latency. Bell “shots” are a Python loop, not ADC captures. Temperatures in mK are a theatrical function of fidelity, not a sensor.

On a real QPU, the following change — and the design claims they can change behind the adapter without rewriting the orchestrator or UI:

  • apply_calibration_update commits a versioned cal table / AWG params and may run a verification sequence taking seconds to minutes.
  • get_device_state reads monitor services, FPGA temps, PLL lock, link status — the stub already sketches these fields in its notes string.
  • get_detuning comes from spectroscopy / Ramsey, not from a hidden vector the process itself owns. The sim’s omniscient detuning is a teaching tool.
  • submit_job for circuits validates schedules, loads waveform memory, arms triggers, waits for completion.
  • Timings and success rates become operational SLOs, not sub-second toys.
  • Persistence — InMemoryJobStore must become Postgres (or equivalent) with retention and goal_id correlation.
Rule of thumb Judge this system by whether a founder can see calibration as a recurring decision with observable cost. Judge a production port by whether the same ToolTraces and metrics still make sense when each apply takes real wall time on real hardware.

2.8 Summary claim

The interface works because it (1) lifts NL goals into a tiny tool catalog, (2) confines device diversity to a six-method adapter, (3) makes calibration a closed loop with explicit thresholds and metrics, (4) publishes trust surfaces (fidelity, mK, drift, 3D device view, ledger), and (5) uses an instrument UI that keeps physics in the visual field while language stays secondary. Everything else in this book is the engineering of that claim on main @ b05005c.

POST/goals

Body GoalRequest { goal: str }. Runs _orchestrator.run_goal, records latencies into MetricsAggregator, returns GoalResponse { goal, results[], traces[], metrics }. Each result is {ok, data, latency_s, error}. Traces are the structured ToolTrace dicts for this execution.

Body { qubit_id?: int=0, target_fidelity?: float }. Calls _calibration.calibrate directly (bypasses planner, still uses the service). Records fidelity in aggregator. Returns success, fidelity, iterations, duration_s, params subset, history.

POST/circuit/bell

Body { shots?: int=1024, qubits?: [0,1] }. Builds a CIRCUIT QPUJob, submits to backend, polls once, returns job_id, counts, metrics — or error.

4.5 Device

GET/device/state

Snapshot: is_ready, readiness_score, qubits, temperatures_mk, coherence_us, readout_fidelity, notes, timestamp, readiness_predicate object.

GET/jobs

Query limit (default 50). Lists recent jobs from backend list_recent_jobs. Documented non-durable.

GET/jobs/{job_id}

400 invalid UUID; 404 unknown. Returns status, type, timestamps, result data, metrics, error.

GET/traces

Most recent orchestrator tool traces (get_last_traces()).

GET/metrics

Union of orchestrator.get_metrics(), MetricsAggregator.snapshot(), and calibration.metrics.to_dict().

4.7 SSE

GET/sse/jobs/{job_id}

DeviceState carries temperatures_mk, coherence_us (T1,T2) per qubit, readout_fidelity, is_ready, notes. readiness_score() averages readout fidelities into 0..1.

5.3 NoisySimulatorBackend

Construction: num_qubits clamped to 1..2, seed (default 42), drift_rate (default 0.002). Maintains _true_params and _applied_params per qubit, an RLock, and an in-memory job store.

Drift

_apply_drift runs on state reads / polls when ≥50 ms elapsed. True params take a Gaussian step scaled by drift_rate and a sinusoidal term sin(now*0.7+q), with clamps per field. This is the lab dynamic the UI visualises: calibration chases a moving target.

Fidelity kernel

_fidelity_from_params builds a squared-error penalty across frequency, amplitude, phase, T1/T2 shortfalls, and readout error, then maps through 0.94*exp(-1.8*err)+0.05, clamped to [0.55, 0.999]. Optional _demo_fid_cap can further ceiling the value for failure demos.

Bell simulation

_simulate_bell_readout draws ideal 00/11, applies readout flips, and depolarises by contrast derived from joint fidelity. Returns counts dict.

Job handling

Calibration jobs run a small local loop (threshold 0.88, max 25) when submitted directly; the preferred path is the CalibrationService via the orchestrator (full metrics + traces). Circuit jobs run Bell (or stub success for unknown circuit names). Cancel flips non-terminal jobs to CANCELLED.

Part 6Calibration & metrics

CalibrationService is an iterative, gradient-free tuner that records the three founder metrics. This part specifies the algorithm, thresholds, failure modes, and what tests assert.

FIG. 6.1Metric definitions again — they are the product dials.

FIG. 6.2Loop structure as implemented in calibration/service.py.

6.1 Algorithm

  1. Read current params; measure initial fidelity; history starts at (0, fid).
  2. For iteration 1..max_iterations:
    • Compute temperature schedule temp = max(0.015, 0.55*(1-progress)).
    • Choose exploration scale (wide early; widen further if patience half-exhausted).
    • Sample neighbour via Gaussian jitter on frequency, amplitude, phase, t1, t2, readout_error with field clamps.
    • Call adapter.apply_calibration_update(candidate); record interface latency.
    • Accept if better than best; else accept worse with probability exp((f-best)/temp).
    • Update best/no_improve; append history; optional on_step callback.
    • Break if best_fid ≥ threshold.
    • If no_improve ≥ patience: restart around best, sometimes with a wide redraw.
  3. Update CalibrationMetrics attempts/successes/time.

6.3 Failure modes

FIG. 6.3Three classes of failure the demos and tests cover.

  • Fidelity cap — POST /demo/fail_next_cal or set_demo_fid_cap. Service reports success=False; fidelity stays below 0.88; attempts still increment.
  • Max iterations / patience cycling — if the basin cannot be climbed in time (or cap intervenes), final message reflects non-convergence.
  • Stub backend — measure_fidelity 0.55 permanently; useful to prove UI/orchestrator don’t assume sim omniscience.

6.4 Test and demo numbers

tests/test_calibration_converges.py asserts fidelity can reach ≥0.80 on the noisy sim with threshold 0.86, and that metrics fields are populated across multi-qubit attempts. tests/test_failure_paths.py asserts capped runs end with success=False and that long-running jobs cancel to CANCELLED. Demos print the three metrics to stdout; they do not claim statistical significance across seeds.

Honesty Historical flakiness: early in development, fidelity could stick near the 0.55 floor while the threshold sat at 0.88 — the wide-basin kernel and exploration schedule exist specifically so the founder demo climbs reliably without becoming a fake always-success path. Caps remain to demonstrate honest failure.

Part 2BTheory addendum — design alternatives rejected

A short record of alternatives considered and rejected while shaping the AI→QPU interface. This is part of the theory of the interface. Knowing what was not chosen clarifies what was.

2B.1 “Just wrap the vendor SDK in LangChain tools”

Rejected as the primary architecture. Vendor SDKs expose dozens to hundreds of calls with pulse-level detail. Dumping them into an LLM tool list creates brittle agents that invent illegal parameter combinations and hide calibration as an incidental side effect of “run_experiment”. This system instead offers five tools and a planner, with calibration as an explicit tool that returns history and metrics. A production system may still wrap vendor calls — but behind the adapter, not as the agent’s entire world.

2B.2 “ChatGPT as the only UI”

Rejected for ops. Language is excellent for composing goals and explaining failures after the fact. It is poor for continuous physical state. Detuning is a spatial relationship; fidelity climb is a time series against a threshold; readiness is a predicate over multiple qubits. Those belong on an instrument stage. Chat remains available via the composer and ⌘K, subordinated to the stage.

FIG. 2B.1Reprise: chat-only vs instrument — the rejected alternative on the left.

2B.3 “One-shot Bayesian optimisation as the calibration product”

Rejected for this system’s thesis. Advanced tuners matter and should plug in as CalibrationService strategies. Shipping a fancy optimiser first would confuse the demo: founders would argue about acquisition functions instead of asking whether the control plane makes calibration a recurring, observable decision. The gradient-free loop is intentionally simple; the metrics and traces are the product.

2B.4 “Hide the simulator’s true params forever”

Partially rejected. Omniscient detuning is unrealistic for hardware — and the stub correctly refuses it. For teaching and founder demos, exposing get_detuning on the sim makes the problem visible on the stage (cyan vs amber). The honesty line in the README states this clearly: the dynamics are representative; the oracle is not.

2B.5 “Require LLM keys for the happy path”

Rejected. Offline-first is a constraint of this system: make demo and the UI must work with zero external services. Optional LLM planning is gated. This keeps CI deterministic and founder laptops unblocked.

Rule of thumb Prefer a boring planner and an honest loop over a clever planner and an opaque loop. Agents can get smarter later; fake observability cannot be fixed by a better model.

Part 5BSimulator physics notes

Additional detail on the noisy simulator’s fidelity kernel, drift update, and Bell contrast — enough to reimplement or replace without reading the UI.

5B.1 Error terms

Let p be applied params and t true params for qubit q. Define:

  • df = |p.frequency - t.frequency|
  • da = |p.amplitude - t.amplitude|
  • dp = absolute wrapped phase difference on [0, π]
  • dt1 = max(0, t.t1 - p.t1) / max(1, t.t1) (penalise claiming too-long T1)
  • dt2 analogous for T2
  • dr = |p.readout_error - t.readout_error|

Composite error:

err = 0.9*df² + 0.7*da² + 0.5*dp² + 0.35*dt1² + 0.35*dt2² + 0.85*dr²
fid = clamp(0.94*exp(-1.8*err) + 0.05, 0.55, 0.999)

Optional demo cap: fid = min(fid, cap) before clamp upper bound still applies via min with cap then clamp.

5B.2 Drift step

On each drift application with elapsed dt and steps = max(1, int(dt*20)):

f_drift = drift_rate * (1 + 0.3*sin(now*0.7 + q))
frequency += N(0, f_drift * steps)   # clamped [4.2, 5.9]
amplitude += N(0, 0.0008 * steps)    # clamped [0.25, 0.75]
phase     += N(0, 0.002 * steps)
t1, t2, readout_error similarly with their sigmas and clamps

5B.3 Bell contrast

joint_f = (f0 + f1) / 2
contrast = clamp(0.5 + 0.48*(joint_f - 0.6)/0.4, 0.02, 0.98)

Ideal bits are 00 or 11 with equal probability; readout flips each bit with the applied readout_error; with probability 1 - contrast the outcome is forced to odd parity (01 or 10).

5B.4 Device state theatre

Temperature: 18 + (1-f)*35 + noise mK. Coherence scales with fidelity. Readout fidelity card: 1 - readout_error*(1.3 - 0.3*f) clamped. Ready iff all readout fidelities > 0.82.

Part 3BArchitecture decision records

ADR-001 — Narrow adapter waist

Context. Real QPUs differ wildly in pulse programming models. Decision. Six synchronous methods on QPUAdapter. Consequences. Orchestrator/UI stay stable; week-1 work is implementing the six methods. Async/hardware batching is a future wrapper concern.

Part 2CTheory — observability as a trust protocol

Extends Part 2: why traces + metrics + drift form a protocol, not a dashboard aesthetic.

2C.1 Three audiences, one ledger

A founder watching the demo needs to see that calibration costs time and sometimes fails. An operator needs to see whether the device is ready and what the last tool did. An agent needs machine-readable ToolResults and stable tool names. The ToolTrace buffer and /traces endpoint serve all three if the UI does not invent a parallel narrative channel.

2C.2 What would falsify the design

  • Calibration “success” without a fidelity history that crossed the threshold.
  • UI READY state disagreeing with /device/state.is_ready for the same poll.
  • Traces that do not match tools actually invoked (LLM fiction).
  • Interface latency that never samples because applies are skipped.
  • A hardware port that requires rewriting page.tsx to show drift.
Rule of thumb If swapping the adapter requires redesigning the ledger, the waist was too wide. If swapping the planner requires redesigning metrics, the metrics were tied to NL rather than to tools.
